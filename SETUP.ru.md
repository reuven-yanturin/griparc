# Подключение Supabase и аналитики

Код уже отправляет заявки и события воронки в Supabase. Нужно подключить реальный проект; PostHog подключен через серверный HTTP API, без установки браузерного SDK.

## 1. Проект Supabase

Создайте проект в своем аккаунте [Supabase](https://supabase.com/dashboard). Если проект уже есть, используйте его. Для аудитории США можно выбрать регион в США.

В SQL Editor выполните сначала `supabase/migrations/001_validation.sql`, затем `supabase/migrations/002_posthog_conversion_status.sql` **по одному разу**. Если первая миграция уже применена, выполните только вторую. Это создаст таблицы `early_access_leads`, `funnel_events`, `request_limits` и функции записи. Публичный доступ к таблицам закрыт; запись выполняется сервером сайта.

## 2. Локальное подключение

В этой рабочей копии уже подготовлен `web/.env.local`: секрет для защиты форм сгенерирован, поля подключения к Supabase пока пустые. Файл исключен из Git. Для новой копии проекта сначала скопируйте `.env.example` в `.env.local` и сгенерируйте `FORM_SIGNING_SECRET` командой `openssl rand -hex 32`.

Заполните в `.env.local`:

```dotenv
SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
SUPABASE_SECRET_KEY=sb_secret_...
```

Project URL и серверный Secret key доступны в настройках проекта Supabase. Для старого ключа `service_role` вместо `SUPABASE_SECRET_KEY` можно использовать `SUPABASE_SERVICE_ROLE_KEY`. `anon` и publishable key для этой серверной интеграции не подходят. Секретный ключ не нужно отправлять в чат или добавлять в переменные `NEXT_PUBLIC_*`.

Из папки `web` выполните:

```sh
npm run check:supabase
npm run dev
```

Проверка не выводит ключи, не читает персональные записи и не создает тестовые заявки. Если настройки окружения менялись при запущенном сайте, перезапустите сервер.

## 3. Проверка заявки и аналитики

1. Откройте `/?variant=pullup&utm_source=manual_test`.
2. Пройдите анкету, откройте результат и ранний доступ.
3. Отправьте одну заявку с вашим тестовым email и согласием.
4. В Table Editor проверьте `early_access_leads` и `funnel_events`.
5. Повторите заявку с тем же email: второй лид и повторная конверсия появиться не должны.

Подтвержденные регистрации и событие `early_access_submitted` записываются одной транзакцией. Остальные события — просмотры страницы, шаги анкеты, просмотр цен и выбор плана — записываются через `/api/events`. Email, количество повторений и оборудование в аналитику не попадают.

Для проверки событий браузер не должен отправлять Do Not Track или Global Privacy Control: сайт уважает эти настройки, и при их наличии аналитика отключается. Заявка при этом сохраняется.

## 4. Где смотреть результат

В SQL Editor используйте SELECT-запросы из `supabase/reporting.sql`:

- посетители и этапы воронки отдельно для beginner и pullup;
- регистрации по цели, опыту и интересу к тарифам;
- количество регистраций с завершенной анкетой.

В конце файла есть отдельные DELETE-команды обслуживания. Выполняйте их только для очистки просроченных ограничителей и событий старше 90 дней; настройте ежедневный запуск до начала эксперимента.

Эта аналитика хранится в вашем Supabase. Для визуальных графиков события дополнительно отправляются в PostHog после его настройки.

## 5. PostHog: подключение и графики

1. Создайте аккаунт на [PostHog](https://posthog.com/) и проект GripArc. Для US Cloud в коде уже указан нужный адрес. Если выберете EU Cloud, замените его на EU-адрес ниже.
2. Используйте Product Analytics / Insights для графиков по нашим событиям. В настройках проекта скопируйте **Project API key**. Personal API key здесь не нужен. Не вставляйте предложенный onboarding-скрипт в сайт: интеграция уже реализована.
3. Заполните `.env.local` и переменные окружения Vercel:

```dotenv
POSTHOG_PROJECT_API_KEY=ВАШ_PROJECT_API_KEY
POSTHOG_HOST=https://us.i.posthog.com
# Для EU Cloud вместо US: https://eu.i.posthog.com
```

4. Примените миграцию `002_posthog_conversion_status.sql` до запуска нового кода и перезапустите сайт.
5. Откройте сайт и пройдите анкету. В PostHog проверьте появление событий, затем создайте funnel из событий:

`landing_view` → `assessment_started` → `assessment_completed` → `results_viewed` → `pricing_viewed` → `early_access_submitted`.

6. Для сравнения двух вариантов добавьте Breakdown по event property `marketing_variant`. Сохраните также короткую воронку `landing_view` → `early_access_submitted`: на сайте доступна прямая регистрация без анкеты.
7. Добавьте графики `plan_selected` по `selected_plan`, заявок по `selected_goal` и по `utm_source`. В PostHog distinct ID соответствует вкладке браузера, а не уникальному человеку.

Новые заявки отправляются в PostHog только после успешного сохранения и только один раз для каждого email. В PostHog не уходят email, подробные ответы анкеты, IP посетителя или записи сессий. Do Not Track и GPC отключают отправку. Пустой API key оставляет аналитику только в Supabase.

При сбое PostHog заявка все равно сохраняется в Supabase. Отправка ограничена 1,5 секунды и не повторяется автоматически; потерянную внешнюю копию события можно заметить, сверив данные с Supabase. Хранение данных PostHog настраивается отдельно: очистка Supabase не удаляет копии в PostHog.

## 6. Публикация

В Vercel укажите Root Directory: `web`. Добавьте те же серверные значения `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `FORM_SIGNING_SECRET` и публичный адрес `NEXT_PUBLIC_SITE_URL=https://griparc.site` **если этот домен назначен сайту**; иначе укажите настоящий адрес публикации. Контакт по умолчанию: `support@griparc.site`.

После изменения переменных выполните новый deploy и повторите тест на опубликованном сайте. Локальный `.env.local` автоматически не переносится в Vercel.
